## Проектирование технологической архитектуры

1. Горизонтальное масштабирование предпочтительнее, так как позволяет увеличивать производительность и отказоустойчивость путем добавления экземпляров.

2. Приложения разворачиваются в нескольких зонах доступности (Центральная Россия, Урал, Дальний восток) для обеспечения отказоустойчивости и требований к задержке для пользователей из разных частей страны.
   1. В каждом регионе независимый кластер Kubernetes для изоляции сбоев (повышения отказоустойчивости) и соблюдения требований по RTO.
   2. Глобальная балансировка нагрузки с помощью DNS с GeoIP для направления пользователей в ближайший регион. В каждом регионе свой балансировщик нагрузки (Cloud Load Balancer), который распределяет трафик между нодами кластера. Health checks настроены в GeoDNS, в каждом регионе на уровне балансировщика нагрузки (проверка состояния эндпоинтов в приложении) и в Kubernetes (liveness и readiness пробы).
   3. При недоступности региона, DNS перенаправляет пользователей в другой доступный регион. Используется active-active фейловер-стратегия для обеспечения требований по RTO.
   4. Используется BDR для multi-master репликации между разными регионами. В каждом регионе имеются локальные синхронные и асинхронные реплики для повышения доступности внутри региона, распределения нагрузки и соблюдения требований по RPO.
3. Для обеспечения консистентности нужно минимизировать конфликты, для этого используется шардирование по регионам, т.е. каждая запись привязана к региону и в основном пишется в своем регионе, а в других регионах она доступна для чтения и обновляется асинхронно.
